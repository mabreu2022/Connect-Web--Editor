# Plano de Implementação - Loja / Marketplace de Componentes Nativos (Pix & Aprovação)

Este plano descreve a arquitetura, modelagem de dados no Firebird 5.0, endpoints do backend em Node.js e componentes do frontend em React para criar uma loja de componentes nativos adicionais que os usuários podem adquirir via PIX.

---

## Modelagem de Dados (Firebird 5.0)

Criaremos três tabelas adicionais no banco de dados Firebird 5.0 da VPS:

1. **`TB_COMPONENTS`**: Catálogo de componentes disponíveis para compra.
   - `COM_ID`: `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
   - `COM_TITLE`: `VARCHAR(255)`
   - `COM_DESCRIPTION`: `VARCHAR(1000)`
   - `COM_CATEGORY`: `VARCHAR(100)` (ex: 'sections', 'forms', 'ui')
   - `COM_PRICE`: `DECIMAL(10, 2)`
   - `COM_THUMBNAIL_URL`: `VARCHAR(1000)`
   - `COM_PAYLOAD`: `BLOB SUB_TYPE TEXT` (Estrutura JSON do nó e filhos)

2. **`TB_ORDERS`**: Pedidos de compra.
   - `ORD_ID`: `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
   - `ORD_USU_ID`: `INTEGER` (Referência a `TB_USUARIOS`)
   - `ORD_COM_ID`: `INTEGER` (Referência a `TB_COMPONENTS`)
   - `ORD_STATUS`: `VARCHAR(20)` (ex: 'pending', 'paid', 'approved', 'rejected')
   - `ORD_COMPROVANTE`: `BLOB SUB_TYPE TEXT` (Base64 da imagem do comprovante Pix)
   - `ORD_CRIADO`: `TIMESTAMP DEFAULT CURRENT_TIMESTAMP`
   - `ORD_ATUALIZ`: `TIMESTAMP DEFAULT CURRENT_TIMESTAMP`

3. **`TB_USER_COMPONENTS`**: Relação de permissão/concessão perpétua de acesso aos componentes.
   - `USC_ID`: `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
   - `USC_USU_ID`: `INTEGER` (Referência a `TB_USUARIOS`)
   - `USC_COM_ID`: `INTEGER` (Referência a `TB_COMPONENTS`)
   - `USC_CONCEDIDO`: `TIMESTAMP DEFAULT CURRENT_TIMESTAMP`
   - *Constraint*: `CONSTRAINT UNQ_USC_USU_COM UNIQUE (USC_USU_ID, USC_COM_ID)`

## Proposta de Endpoints (Backend)

Criaremos a rota `backend/src/routes/store.routes.js` e montaremos em `/api/store` no `server.js`:

* **`GET /api/store/components`** (Autenticado): Retorna o catálogo completo de componentes e inclui uma tag `adquirido: true/false` baseando-se na existência de registro correspondente em `TB_USER_COMPONENTS` para o usuário logado.
* **`POST /api/store/checkout`** (Autenticado): Cria um registro com `status = 'pending'` na tabela `TB_ORDERS`. Recebe `{ componentId: number, comprovante: string (base64) }`.
* **`GET /api/store/admin/orders`** (Autenticado + Admin): Lista todas as compras pendentes com comprovantes, detalhes do usuário e nome/valor do componente.
* **`POST /api/store/admin/orders/:id/approve`** (Autenticado + Admin): Aprova um pedido. Altera status para `'approved'` na tabela `TB_ORDERS` e insere o registro correspondente em `TB_USER_COMPONENTS` de forma transacional.
* **`POST /api/store/admin/orders/:id/reject`** (Autenticado + Admin): Rejeita o pedido. Altera o status para `'rejected'`.

## Front-End (React)

1. **A Loja Virtual (Interface Bento Grid / Modal):**
   * Acessível pelo cabeçalho ou menu lateral.
   * Exibe cards modernos de componentes, preços, botão de "Comprar (Pix)" e área para o usuário enviar o comprovante (drag-and-drop de arquivo ou upload direto).
   * Componentes já adquiridos mostrarão um selo de **"Adquirido / Desbloqueado"**.

2. **O Painel Administrativo:**
   * Uma nova seção administrativa acessível no topo (para administradores) que exibe as solicitações pendentes, a imagem do comprovante Pix e botões de **Aprovar** e **Rejeitar**.

3. **Integração com a Ferramenta de Edição (ComponentPalette):**
   * Ao carregar o editor, o sistema busca os componentes que o usuário possui via `GET /api/store/components`.
   * Os componentes adquiridos aparecerão dinamicamente no painel de componentes sob uma nova categoria **"✨ Loja (Adquiridos)"** com o selo **"Lifetime / Desbloqueado"**. Eles podem ser arrastados e clicados normalmente no Canvas.

## Verificação e Instalação

1. **Inicialização Automática (Self-Installing Schema):**
   * Ao iniciar o backend, uma rotina verificará a existência das tabelas no Firebird 5.0 e as criará se não existirem.
   * Inserirá 3 componentes padrão no banco (ex: Tabela de Preços Premium, Form Avançado, Galeria Dinâmica) caso a tabela de componentes esteja vazia.
2. **Build Local e Publicação:**
   * Compilaremos o projeto localmente para assegurar a tipagem estrita do TypeScript.
   * Publicaremos na VPS de produção com reinício PM2.
